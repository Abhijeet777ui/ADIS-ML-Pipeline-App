ADIS (Automated Data Intelligence System)
PROJECT ARCHITECTURE & FILE DOCUMENTATION
=================================================

This document serves as a comprehensive guide to understanding the ADIS codebase. It breaks down every file, what its technical purpose is, and the broader "why" behind the engineering decisions made during development.

-------------------------------------------------
1. THE CORE APPLICATION & ROOT DIRECTORY
-------------------------------------------------

File: app.py
- What it is: The interactive Streamlit frontend.
- What we did: We built a multi-tab dashboard (Ingestion, Cleaning, EDA, Engineering, Modeling, and Vulnerabilities). It takes a user's CSV upload, writes it temporarily to the disk (`temp_data.csv`), hands it to the `ADISPipeline`, and stores the returned structured dictionary in Streamlit's `session_state`. 
- Why we did it: Instead of a messy Jupyter Notebook, a frontend web app democratizes access to the AI. Storing the pipeline output in `session_state` ensures that when users flip between tabs, the expensive ML models don't have to re-train. It also translates the JSON explanations into human-readable alerts and Plotly charts.

File: README.md
- What it is: The public-facing project presentation.
- What we did: Outlined the features, edge cases handled, and the MLOps/API nature of the backend. Included instructions on how to run. Added "Known Limitations" (like lack of deep learning or NLP).
- Why we did it: A GitHub repository without a robust README is ignored by recruiters and engineers. By explicitly writing down the limits of the software, it demonstrates senior-level maturity.

File: requirements.txt
- What it is: Dependency locking.
- What we did: Listed pandas, numpy, scipy, scikit-learn, streamlit, and plotly. We specifically removed `pathlib` because it conflicts with standard library rules in cloud environments.
- Why we did it: Guarantees that the app deploys seamlessly on Streamlit Community Cloud without dependency resolution errors.

-------------------------------------------------
2. THE ADIS BACKEND PIPELINE (Inside /adis/)
-------------------------------------------------

File: adis/pipeline.py
- What it is: The central nervous system of the project.
- What we did: Created the `ADISPipeline` class. It manages the linear flow of data: Ingestion -> Cleaning -> EDA -> Engineering -> Model Recs -> Selection -> Benchmarking -> Critic. 
- Why we did it: Modularity. If we put all this code in one file, it would be thousands of lines long and impossible to debug. The pipeline acts as a simple coordinator that holds a "report" dictionary building up a story step-by-step. It also handles the `save_report()` function to export JSON artifacts mimicking an enterprise MLOps backend.

File: adis/ingestion.py
- What it is: The data loader.
- What we did: Loads the CSV safely, handles parsing errors, and calculates memory usage. Detects logical data types (boolean formats, datetimes, strict numerics versus categoricals).
- Why we did it: Pandas default `read_csv` can make poor assumptions (like treating "True/False" strings as plain text). This file ensures the foundation for all subsequent math is built on correct data types.

File: adis/cleaning.py
- What it is: The janitor of the dataset.
- What we did: Implemented flexible imputation (falling back from KNN to automatic median/mode), removes duplicate rows, fixes messy currency strings, and clips outliers using IQR/Z-scores.
- Why we did it: "Garbage in, garbage out." If outliers skew the loss functions of our models or missing values crash scikit-learn training loops, the pipeline fails. This guarantees the data is structurally sound.

File: adis/eda.py (Exploratory Data Analysis)
- What it is: The statistical profile analyzer.
- What we did: Calculates skewness and kurtosis. Checks for target-class imbalance ratios. Identifies high cardinality (too many unique categorical values).
- Why we did it: Gives context. For example, if we have a severe class imbalance (e.g. 99% benign, 1% fraud), the downstream algorithms *must* know this so they don't blindly predict the majority class.

File: adis/feature_engineering.py
- What it is: The pattern amplifier.
- What we did: Breaks down date columns into 'Year', 'Month', 'Day'. Handles safe label encoding and categorizations for the models to digest.
- Why we did it: Machine learning models are just giant math equations; they cannot parse the string "January" or understand non-linear dates without us mathematically restructuring them.

File: adis/model_recommendation.py
- What it is: The strategic planner.
- What we did: Detects the `problem_type` (Is the target continuous? -> Regression. Are there 2 unique targets? -> Binary Classification). Then looks at row counts/features to prioritize a list of models to try (e.g. Random Forest vs Logistic Regression). 
- Why we did it: Standard AutoML often brute-forces 50 models wasting time/resources. This step introduces intelligent heuristics to only pick the top 3-4 most viable algorithms for the data size and type.

File: adis/feature_selection.py
- What it is: The noise reducer.
- What we did: Uses Mutual Information scores to rank features against the target. Drops features with near-zero variance, and deletes one half of highly-correlated pairs.
- Why we did it: To fight the "Curse of Dimensionality." Feeding a model 500 columns of garbage creates overfitting and noise. This logically isolates only the columns that mathematically hold predictive power.

File: adis/benchmarking.py
- What it is: The arena.
- What we did: Takes the recommendations, trains them all against the chosen `target_column` using basic validation holding, evaluates metrics (R2, Accuracy, ROC-AUC), and extracts feature importances.
- Why we did it: To prove computationally which architecture handles the specific nuances of the data the best, returning the ultimate champion.

File: adis/critic.py
- What it is: The elite vulnerability scanner (The "Diagnosis Engine").
- What we did: Grabs the final JSON output of the entire pipeline and cross-references signals. It detects "Metric Illusion" (high accuracy on imbalanced data but poor AUC), "Target Leakage" (one feature holding >70% importance driving 99% accuracy), and "Data-Starved Overfitting."
- Why we did it: This is what separates this project from beginner tutorials. It models the behavior of a Senior Machine Learning Engineer reviewing a Junior Developer's pipeline. It doesn't just look at metrics; it looks at metrics *in context* of the dataset to warn the user about production readiness.
